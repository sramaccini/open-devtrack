# ADR-21: Public REST API and outgoing webhooks

Status: Proposed (12 November 2026) — F5, epic E11

## Context

E11 of the project plan asks for a documented public REST API (OpenAPI 3.1) and outgoing webhooks. The plan's stack
names springdoc-openapi for the definition, which Quadrava Studio can also import to generate data sources. Its
non-functional requirements still hold: «no token in the browser», ASVS level 2, p95 < 300 ms for lists and details.

What there is today:

- About 100 endpoints under `/api` (projects, issues, comments, attachments, links, watchers, workflows, boards,
  sprints, search, filters, reports, notifications). The screens call them with the session cookie of authz-library.
  - They are written for the screens: `_perm` on rows and forms, the `version` of a resource for optimistic locking
    (412), Problems (RFC 9457) in English.
  - No OpenAPI definition is generated: springdoc is not a dependency.
- Tools without a session (the Quadrava CLI, the registry kit) use a Keycloak access token on `/registry/**` only.
  - The filter chain is OpenDevTrack's own (`platform/BearerTokenSecurity.java`) and resolves the token to the same
    permissions as a session.
  - It is temporary until authz-library offers bearer access itself (request A4).
- Domain events after the commit, kept by the Event Publication Registry of Spring Modulith on PostgreSQL:
  `IssueCreated`, `IssueChanged` (with the field changes), `IssueDeleted`, `CommentPosted`, `AttachmentAdded`,
  `AttachmentRemoved`, `SprintStarted`, `SprintCompleted`.
- `notification` already sends mails from an outbox with retries (ADR-18). Webhooks need the same: something outside
  that may be slow or down.

## Decision

### A. The public API

1. **One API, the one the screens use.** The public API is `/api` as it is. It is not a second layer to keep in step.
   `_perm` stays in the answers (it tells a client what the user may do), as does `version` (412 when the resource
   changed meanwhile).
2. **An OpenAPI 3.1 definition generated by springdoc** at `/v3/api-docs`, readable by every authenticated user. It
   lists the paths, the request and answer records, the Problems, and the permissions each path needs.
   - The paths are grouped by module.
   - Those that serve only a screen (the counts of the personal dashboard, the lookups with `q`) are marked
     `x-internal: true`. They work the same, but may change without notice.
3. **The definition is a contract kept in the repository**: `docs/openapi.json`. A test generates it and fails when
   it differs from the committed file, so every change to the API shows up in review.
   - Within 1.x a public path or field is not removed or renamed. It may be marked `deprecated` and removed in the
     next major version.
   - Adding paths and fields is allowed.
4. **Authentication for clients: a Keycloak access token** in `Authorization: Bearer`, resolved to the same
   permissions as a session. This is the chain of `/registry/**`, extended to `/api/**`.
   - People use the token of their own user.
   - Machines use a **service account**: a Keycloak client with client credentials, given roles in a tenant as any
     user is. A service account is created by an admin of the tenant.
   - The tenant of a request is the header `X-Tenant`, checked against the tenants of the user; without it, the last
     one used.
   - No cookie travels with a bearer request, so writes need no CSRF token. A request with both a cookie and a bearer
     is refused.
   - The browser keeps the session cookie and never holds a token, as the plan asks.
   - This is A4 in authz-library. Until it ships, OpenDevTrack extends its temporary chain to `/api/**`, written down
     there. Personal access tokens (A6) are asked of authz-library but are not needed for 1.0.
5. **Limits.** Lists are paged as today (at most 200 rows). Bearer requests are rate limited per user or client, 600
   a minute by default, with a 429 Problem and `Retry-After`; the counter comes with A4. Until then the limit is left
   to the ingress (documented in the Helm values).
6. **Documentation**: a page in `docs/api.md` covers getting a token (user, service account), the tenant header,
   versions and 412, paging, Problems and the limits, with `curl` examples. The definition can be read with any OpenAPI
   viewer; the instance serves no Swagger UI.

### B. Outgoing webhooks

7. **Per project, by an admin of the project** (`odt.project.edit`). A webhook has:
   - a name;
   - an HTTPS URL;
   - the events it wants, `*` for all;
   - a signing secret, generated by OpenDevTrack and shown once;
   - an `active` flag.

   A project has at most 10 webhooks. Module `integration`, new: it listens to the events of the other modules and
   no module depends on it.
8. **Events** (the payload names them in lower case, `<resource>.<action>`):
   - `issue.created`, `issue.changed` (with the field changes, as in the history), `issue.deleted`;
   - `comment.posted`;
   - `attachment.added`, `attachment.removed`;
   - `sprint.started`, `sprint.completed`.
   - The project's events only. Changes to the configuration (workflows, boards, members) are not sent in 1.0.
9. **Payload**: JSON, small and stable, with no copy of the resource.

   ```json
   { "id": "<uuid of the delivery>", "type": "issue.changed", "time": "2026-11-12T10:15:00Z",
     "tenant": "ACME", "project": "WEB", "actor": "mario.rossi",
     "data": { "key": "WEB-42", "url": "https://…/api/issues/WEB-42",
               "changes": [{ "field": "status", "from": "todo", "to": "in_progress" }] } }
   ```

   - The receiver reads more through the API when it needs it.
   - The text of a comment is not sent: only its id and the issue.
   - The fields of `data` follow the same 1.x rule as the API, and are part of `docs/api.md`.
10. **Signature**, as the Standard Webhooks specification has it (a short, public, well-known scheme). Each request
    carries the headers `webhook-id`, `webhook-timestamp` and `webhook-signature`: an HMAC-SHA256 of
    `id.timestamp.body` with the secret, `v1,<base64>`. A receiver refuses a timestamp older than 5 minutes. The
    secret can be rotated: the old one also signs for 24 hours.
11. **Delivery from an outbox**, as the mails of ADR-18:
    - a listener after the commit writes one row per matching webhook in `odt_integration.delivery`;
    - a scheduled job posts what is due, with a 10 s timeout and no redirects followed;
    - a 2xx is a success;
    - anything else is retried after 1 min, 5 min, 30 min, 2 h, 6 h and 12 h, then given up.
    - After 3 days of deliveries given up in a row, the webhook is turned off and its admins get an in-app message.
    - Order is not guaranteed: `time` and `id` let a receiver sort and drop duplicates.
    - Deliveries are kept 30 days.
12. **SSRF**: the URL must resolve to a public address.
    - Loopback, private, link-local and metadata ranges are refused when saving and again when sending, since DNS can
      change.
    - `odt.webhooks.allow-private` (off by default; on in the development stack and the e2e) lets a local receiver be
      used.
    - Only `https`, except where that property is on.
13. **Screens**:
    - the Webhooks section of `project-detail`: a table with name, URL, events, active and the last delivery, with
      New, Edit, Remove, «Rotate secret» and «Send a test» (a `ping` event);
    - a screen `webhook-detail` with the last 50 deliveries (event, status, attempts, answer code, when) and
      «Deliver again».

    No new Quadrava component is needed.

## Alternatives considered

- **A separate `/api/v1` for clients**, shaped apart from the screens. Cleaner names, but two APIs to keep in step,
  test and document. The rule of point 3 gives clients stability without a second layer.
- **Personal access tokens issued by OpenDevTrack.** Handy for scripts, but they are credentials: stored, hashed,
  revoked, audited. That is security code, which belongs to authz-library (AGENTS.md § 2), so they are asked there
  (A6).
- **API keys per project.** Simple, but they act as nobody: permissions and the history need a user. A service
  account is a user.
- **Webhooks sent from the listener**, without an outbox: a slow receiver would slow the processing of the events,
  and retries need a store anyway (as for the mails).
- **CloudEvents as the envelope.** Close to the payload above, but its HTTP binding has no signature; Standard
  Webhooks covers the signature, retries and ids in one short text. The fields of point 9 keep CloudEvents names
  (`id`, `type`, `time`), so a later binding stays easy.
- **Full resources in the payload.** Fewer calls for the receiver, but larger messages that leak what the receiver
  may not need, and the API rule would bind every field of every resource twice.

## Consequences

- Dependency springdoc-openapi (`springdoc-openapi-starter-webmvc-api`, the version authz-library uses), the
  generated `docs/openapi.json` and its test.
  - Each path gets annotations for its permission and its Problems where springdoc cannot infer them.
- `platform`: the bearer chain extended to `/api/**` with `X-Tenant` until A4, and the Keycloak realm of
  development, e2e and stack gets a service account client for the tests.
- New module `integration`: migration (`webhook`, `delivery`), listeners, the outbox job, the SSRF check, the API
  under `/api/projects/{key}/webhooks`, screens and texts in English and Italian.
- `docs/api.md`. In the stack, a receiver to see deliveries: Mailpit does not take HTTP, so a small echo container.
- Tests:
  - a client with a service account token (read and write, 403 without permission, 412, the tenant header);
  - the definition in step with the code;
  - a webhook with signature check, retries and give-up on a clock, turning off, the SSRF refusals, `ping`.
- Requests to the dependencies: A4 (bearer access, service accounts, the tenant header, rate limiting) and A6
  (personal access tokens) to authz-library, sent 12 November 2026. Nothing new from Quadrava.
